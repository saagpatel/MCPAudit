# MCPAudit 2.10.1 Release

Release status: approved
Publication decision: GO

MCPAudit 2.10.1 is a backward-compatible patch release for residual
credential-redaction edges, hostile-fleet scan performance, and test/CI
reliability. This document authorizes the exact release-state source for review
and publication gating; tag, GitHub Release, PyPI, MCP Registry, runtime,
deployment, adoption, and user-acceptance claims still require their own live
readbacks.

## 2.10.1 patch

- Close residual free-text redaction edges where terminal escape sequences
  split or supply secret labels, flag dashes, or delimiters. Redact URL userinfo
  separated from its `@` by spaces, tabs, or Unicode spaces.
- Improve hostile-fleet scan performance with a single report redaction per
  scan, faster analysis and parsing, and bounded report-local redaction reuse.
  Standalone renderers still redact fresh input. Detector evidence, schema
  budgets, connection concurrency, deadlines, and process cleanup are unchanged.
- Fix the detector-parity test flake by making direct red-team fixture sampling
  deterministic, independent of global random-number consumption.
- Calibrate hostile performance gate time budgets to the runner using median
  fixture startup/stdio and synthetic report CPU measurements. Preserve published
  case values, RSS and coverage requirements; use `--perf-no-calibration` for
  raw numbers against the published time ceilings.

### Upgrade notes

- Text containing terminal escape sequences may show more `<redacted>` markers.
  Fields with an escape sequence longer than 64 printable bytes are withheld
  conservatively; the same applies to densely escaped fields. Review reports
  before sharing.

## Known issues

- See [Known issues](known-issues.md) for the remaining argv escape-supplied
  inline delimiter and fullwidth flag delimiter redaction edges, sequence
  rollback limits, schema-check coverage, and legacy v1 pins. Redaction remains
  best-effort; arbitrary unlabeled secrets can still be missed.

## Previously in 2.10.0

2.10.0 introduced structural credential redaction, signed-pin sequence gates,
authorization-challenge parsing, read-only shadow review, optional counts-only
OpenTelemetry export, and bounded lab improvements.

### Upgrade notes

- Reports use structural credential redaction (D10). Expect more `<redacted>`
  markers in report text, including some labels next to terminal controls and
  quoted URLs with queries. Redacted schemas are display evidence, not replacement
  execution schemas; review reports before sharing.
- MCP019 and `--inject-check` now describe instruction-shaped text. The wording
  does not establish malicious intent or change the detector's evidence boundary.
- List-tool MCP responses retain their legacy result in the first text block and
  gain a second warning text block, including when warnings are empty, plus additive
  `structuredContent.warnings`. Consumers must tolerate the extra block and field.
- Signed pin manifests gain a monotonic `sequence` (D11). Existing signed manifests
  without it still verify unless a minimum is required; re-sign after review to
  start at 1. Keep `require.pin_min_sequence` or `--pin-min-sequence` outside the
  pin file for one-shot CI rollback protection. A signed manifest with a missing
  trust store reports `MCP027`; restore the trusted public keys before verification.
- Migrate unsigned v2 pins with `pin --refresh SERVER --apply` after key setup and
  review. The preview is unverified; previously signed entries retain fail-closed
  integrity checks. See [Pinning](guides/pinning.md).
- Independently valid multi-line `WWW-Authenticate` challenges and legal empty
  comma elements now permit authorization metadata review (D12). Ambiguous or
  malformed challenges and exhausted limits still withhold that review.
- The frozen `mcp_audit.cli._run_scan_core` compatibility shim remains available
  through 2.x and is scheduled for removal in 3.0. Library integrations should
  use `mcp_audit.engine.run_scan(ScanOptions(...))`.

### Included capability groups

- Structural redaction (D10) traverses typed reports before terminal, JSON,
  SARIF, and HTML rendering. It covers argv values, URL components, schema keys
  and literals, Unicode-obfuscated credentials, and escaped quotes, with free-text
  pattern matching as a fallback. Unlabeled secrets can still be missed.
- Signed pin manifests (D11) carry a monotonic `sequence`; policy
  `require.pin_min_sequence` and CLI `--pin-min-sequence` refuse older or
  unauthenticated baselines. A missing trust store for a signed manifest is
  `MCP027`. Guided unsigned-to-signed migration retains an explicit unverified
  review before replacing the baseline.
- Authorization-challenge parsing (D12) accepts independently valid header lines
  and legal empty comma elements without relaxing ambiguous or malformed input
  rejection. Metadata observations do not prove a completed OAuth flow.
- Read-only `shadow` review (D13a) requires explicit configs and pins, with static
  signature and rollback checks by default. Opt-in metadata connections add drift
  and fleet tool-name collision review; policy and sequence gates reuse the engine.
  It does not update configs, pins, or trust history or provide an enforcing proxy.
- The opt-in `[otel]` library extra (D14) exports redacted reports as counts-only
  report, server, and coverage-check spans with rule-count events, excluding report
  hostnames, identifiers, and evidence payloads. See
  [OpenTelemetry integration](OUTPUT-CONTRACT.md#opentelemetry-integration).
- `fix SERVER --config FILE` (D15) prints dry-run, argument-only JSON Patch
  suggestions for an unpinned `npx -y` package (`pkg@<version you supply>`) and
  for filesystem roots of `$HOME` or `/` (a narrower path you supply). Nothing is
  written to disk; there is no `--write`.
- Coverage plumbing carries project-config connection warnings through every
  `serve` tool response, with additive structured warnings and a warning text
  block; SARIF invocation notifications retain them in both profiles.
- Empty-home CLI output leads with the empty state and coverage summary. MCP019
  uses instruction-shaped-text wording; detector evidence remains a review signal.
- Offline labs add an S256 PKCE finding and authorization-error issuer validation,
  preserve unknown results for missing evidence, and link session-resume transport
  observations. Opt-in negative conformance probes send bounded credential-free
  header requests and loopback-only Origin probes. Shared bounded reads, strict
  JSON decoding, and canonical serialization preserve each lab's own contract.
- CI runs a checksum-verified, pinned actionlint on every pull request. Regression
  tests cover Unicode evidence offsets, process-group probe permissions, compact
  pytest IDs, synthetic key fixtures, and wall-clock assertion hygiene.

## Public-surface boundary and rollback

Release metadata, the Registry descriptor, Action examples, pre-commit example,
and `docs/release-state.json` identify 2.10.1. Until publication completes,
those source references are proposed release identities rather than proof that
any public artifact or Registry entry exists. Retain `mcp-audits==2.10.0` as the
rollback pin and verify installed command identity after rollback.

## Compatibility and claim ceiling

The distribution remains `mcp-audits`; installed commands remain `mcp-audit`,
`mcp-audits`, and `proof-before-action`. Python 3.11–3.13 and the MCP SDK range
`mcp>=2.2.0,<3.0` remain supported. Existing 2.x report contracts remain
additive, with `schema_version` unchanged.

Release-state source can prove repository consistency and bounded local or CI
verification only. It cannot by itself prove a tag, published artifact, Registry
entry, installed runtime, configured invocation, production use, downstream
adoption, interoperability, or human effectiveness. Missing, stale, masked, or
unverifiable external evidence remains `UNKNOWN`.

Local tests and repository consistency establish only the behavior exercised
and release-state metadata consistency. They do not establish publication,
live third-party interoperability, deployment, adoption, or human outcomes. A
clean canary describes only its bounded in-session exercise.
