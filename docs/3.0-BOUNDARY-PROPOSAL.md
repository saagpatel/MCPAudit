# 3.0 Boundary Proposal

Status: implemented for 3.0.0, which is not released yet. The owner approved
the design decisions in section 8 on Oct 12 2026, D22 on Oct 13 2026, O-1 to
O-3 on Oct 14 2026, and O-4 on Oct 31 2026.
This document records what 3.0 removes, splits, and renames, what each change
breaks for users, and which warnings 2.x shipped first so that every break was
visible before an upgrade. Section 7 records what 2.11 and 2.12 shipped and
what is in 3.0.0; section 8 records each decision and the implementation
details that refined it.

## 1. Summary and goals

MCPAudit 2.x ships one distribution, `mcp-audits`, that contains the static and
connected MCP review, eight offline labs, SafeForge, and the standalone Proof
Before Action CLI. It also carries compatibility surfaces that 2.x promised to
keep until 3.0: the legacy `scan` grammar, the hidden `monitor` proxy, the
frozen `mcp_audit.cli._run_scan_core` shim, hidden 2.x command aliases, and
legacy v1 pin entries.

The 3.0 boundary has four goals:

1. Make the default install the security review tool only. Labs and Proof
   Before Action keep their own release notes and threat models, and users who
   do not run them should not install their code or review their changes.
2. Make `check` the one review command. `check` already has the safe default
   (static, no connections) and the newer grammar; `scan` remains the older
   grammar with connect-everything as its default.
3. Delete the surfaces already announced for removal in 3.0: `monitor`
   (deprecated in 2.9), `_run_scan_core` (deprecated since 2.3, scheduled for
   3.0 in 2.10), and v1 pins (owner decision D19).
4. Give every break a 2.x warning, a migration command, and a way to detect it
   before upgrading.

Why now: the compatibility surfaces are each small, but together they keep two
CLI grammars, two pin hash contracts, and an unused proxy in the review path.
2.11 makes the v1 pin warning universal (D19), so 3.0 is the first release
where every announced removal has had a warning in a shipped release.

### `check` and `scan` today

`check` (`src/mcp_audit/check_cli.py`) reads an explicit `--config FILE` only,
or the fixed supported-client allowlist, statically. `--connect` connects to
exactly one identity selected with `--server CLIENT:SCOPE:NAME`. `--json`
writes JSON to stdout and `--output-json FILE` writes a file. `check` runs the
injection, trifecta, and shadowing detectors only when a card is requested on
a connected check, and exposes none of the other opt-in detectors.

`scan` (`src/mcp_audit/_core_cli.py`, implemented by `scan_cli._run_scan`)
discovers all supported configs and connects to every workstation server by
default. It has options that `check` lacks:

- Connection scope and budgets: `--skip-connect`, `--config-only`,
  `--connect-project-configs`, `--clients a,b`, `--timeout`,
  `--max-concurrency`.
- Opt-in detectors: `--inject-check`, `--ssrf-check`, `--ssrf-allowlist`,
  `--egress-check`, `--egress-allowlist`, `--multi-tenant-hosts`,
  `--pin-check`, `--trifecta-check`, `--shadow-check`, `--escalation-check`,
  `--provenance-check`, `--integrity-check`.
- Higher-reach modes: `--verify-artifacts`, `--download-artifacts`,
  `--llm-analysis`, `--canary-check`, `--canary-calls`,
  `--canary-identities`, `--canary-safe-tool`.
- Output: `--json PATH` (a path, so `--json -` writes a file named `-`),
  `--sarif-profile`, `--redact`, `--verbose`.

So `scan` cannot become an alias of `check` until `check` can express these
options. Section 4 covers that.

### Pins

`src/mcp_audit/pinning.py` writes `pin_schema: 2` entries hashed over
`mcpaudit.tool-surface.v2`, with an optional signed `mcpaudit.pin-manifest.v1`.
It still reads v1 entries: tool rows without `pin_schema` (default 1), hashed
by `_legacy_tool_hash` over name, description, and input schema with
`canonical_json_bytes(..., legacy=True)`. `_is_legacy_entry` identifies a
genuine v1 entry; mixed entries hold v2 rows plus retained v1 rows. Today a v1
entry warns `pin_schema_outdated` when the baseline is trusted, and is
withheld (`pin_baseline_withheld`) only when trusted pin keys exist. Canary
comparison drops v1 rows through `uncovered_legacy_tools`. In 2.11, item R-6
makes every v1 read warn with the `pin --refresh` migration command (D19).

## 3. Proposed package split

### Distributions

| Distribution | Import package | Console scripts | Contents |
| --- | --- | --- | --- |
| `mcp-audits` | `mcp_audit` | `mcp-audit`, `mcp-audits` | Core |
| `mcp-audits-labs` | `mcp_audit_labs` | none | Eight lab topics (including the enforcement fixture), conformance probe, SafeForge |
| `mcp-audits-proof` | `proof_before_action` | `proof-before-action` | Proof Before Action |

The names `mcp-audits-labs` and `mcp-audits-proof` are reserved on PyPI with
0.0.1 placeholders that only point at `mcp-audits` (decision D21).

`mcp-audits` stays the core distribution under its current name (see
[decision Q1](#q1-what-mcp-audits-installs)). It gains extras:

- `mcp-audits[labs]` installs `mcp-audits-labs` at the same version.
- `mcp-audits[proof]` installs `mcp-audits-proof` at the same version.
- `mcp-audits[all]` installs both, plus the existing `watch`, `llm`, and `otel`
  extras.

So `uv tool install mcp-audits` gives the review CLI, `serve`, `watch` (with
the `watch` extra), pins, policy, and all report formats. The umbrella install
that matches 2.x contents is `uv tool install 'mcp-audits[labs,proof]'`; because
`uv tool` exposes only the root package's scripts, Proof Before Action users
install it as its own tool with `uv tool install mcp-audits-proof`.

### Module assignment

- Core: the 75 core modules listed in section 2, minus `monitor.py`, the
  legacy `scan` engine path in `scan_cli.py` (replaced by the Q4 interceptor),
  and the `_run_scan_core` shim. Plus `mcp_audit.oauth_urls`, added in 2.12,
  which holds the OAuth URL helpers, limits, and canonical posture JSON
  encoding that `probe.py` previously imported from
  `authorization_posture_models.py` (`MAX_AUTHORIZATION_SERVERS`,
  `MAX_FETCHES`, `expected_authorization_metadata_url`,
  `expected_resource_metadata_url`, `origin`, `require_https_url`,
  `canonical_json_bytes`). The lab model imports them from core.
- Labs: the 34 lab and SafeForge modules listed in section 2, under
  `mcp_audit_labs`. SafeForge is a lab by evidence: its own threat model lives
  in `docs/labs/`, it targets a macOS Seatbelt research profile, and no user
  guide or Action recipe depends on it.
- Proof Before Action: the five `proof_*` modules under `proof_before_action`,
  with `__version__` read from its own distribution metadata instead of
  `mcp_audit`.

`skills scan` stays in core: it is an everyday review of local inputs, imports
only `redaction` and `__version__`, and is not documented as a lab.

### Dependency direction

```text
proof_before_action        (no MCPAudit imports)

mcp_audit_labs  ------>  mcp_audit (core)  ------>  third-party only
```

- Core imports nothing from labs or Proof Before Action. After the URL helper
  move, the only upward reference is the `lab` command registry, which names
  lab modules by string and imports them only when a lab command runs (see
  [Q8](#q8-how-core-finds-lab-commands)). That matches how core already treats
  the optional `watchfiles` and `anthropic` imports.
- Labs import core only through modules that are already shared today:
  `__version__`, `canonical`, `models`, `api`, `report`, `terminal_text`, the
  `oauth_urls` module, and the `probe` request helpers. 2.12 made those `probe`
  helpers public (`json_object`, `post_url`, `request_sync`, `Response`); they
  are internal-but-shared, safe because labs pin core to the exact same
  version. A 2.12 import-graph test checks that core never imports lab or Proof
  modules.
- Proof Before Action imports nothing from core. It depends only on `click`,
  `pydantic`, and `pyyaml`.
- There are no import cycles. The extras on `mcp-audits` create a
  metadata-level loop (`mcp-audits[labs]` requires `mcp-audits-labs`, which
  requires `mcp-audits`); installers resolve this pattern routinely, and no
  code imports upward through it.

Third-party dependencies per distribution:

- Core: `click`, `rich`, `anyio`, `json5`, `mcp`, `cryptography`, `pydantic`,
  `pyyaml`, with optional `watch`, `llm`, `otel`.
- Labs: `mcp-audits==X.Y.Z`; the `mcp` SDK, `anyio`, `pydantic`, `click`, and
  `rich` arrive through core.
- Proof: `click`, `pydantic`, `pyyaml`.

| --- | --- | --- |

### Installation and versioning

All three distributions release in lockstep from this repository with one
version number (see [Q3](#q3-versioning)). Labs pin `mcp-audits==X.Y.Z`
exactly; the extras on `mcp-audits` pin the other two exactly. One release
checklist run builds and verifies three wheels and three sdists from one
approved commit, and `docs/release-state.json` records the shared version.
`server.json` keeps `mcp-audits` with `serve`, so the MCP Registry identity
does not change.

Publication order is core, then labs, then proof: `mcp-audits`,
`mcp-audits-labs`, `mcp-audits-proof`. No tag, GitHub Release, Registry entry,
or Action ref advances until all three pinned wheels and sdists are published
and verified. If an upload or readback fails, every public release pointer
stays frozen and the partial-publication recovery in the
[release checklist](../maintainers/RELEASE-CHECKLIST.md#partial-publication-recovery)
applies: resume only the missing files from the original approved bytes after
a transient failure, or yank and cut a new lockstep patch version when an
artifact is wrong.

2.12 shipped the release-tooling groundwork without splitting the package:
`scripts/verify_release.py` accepts a distribution contract (`--distributions
FILE`) listing each distribution, module, and scripts in publication order;
built wheels and sdists must match a reference build of the approved commit
file for file, with exact `Requires-Dist`; and the build backend's package root
and Proof's source-provenance path are configurable. 3.0 activates that
tooling: a committed `release/distributions.json` three-distribution contract,
a commit-first verifier, and a publish workflow that builds a six-file manifest
and uploads core, labs, then proof with a readback after each (section 7 and
[release tooling](#release-tooling-details) in section 8).

## 4. CLI changes

### `scan` becomes a legacy interceptor over `check`

In 3.0, `check` is the primary name in help, docs, the Action, and the
pre-commit hook. `scan` is neither a bare alias nor a second engine path. It is
a frozen translation table over `scan`'s option names (decision
[Q4](#q4-what-scan-means-in-30)), implemented in 2.12 as
`src/mcp_audit/scan_translation.py` and consumed by the 3.0 interceptor. 3.0
extends it with D22's exact static translation (D-2) and the replacement
command printed on exit 2 (X-2).

`check` first had to express what `scan` users run. 2.12 added these to
`check`, additively:

- The opt-in detector flags, with the same names and meanings:
  `--inject-check`, `--ssrf-check`, `--ssrf-allowlist`, `--egress-check`,
  `--egress-allowlist`, `--multi-tenant-hosts`, `--pin-check`,
  `--trifecta-check`, `--shadow-check`, `--escalation-check`,
  `--provenance-check`, `--integrity-check`.
- The higher-reach modes with the same names: `--verify-artifacts`,
  `--download-artifacts`, `--llm-analysis`, and the `--canary-*` options.
  Canary requires `--config FILE` with a selected connection and no discovery.
- `--sarif-profile`, `--redact`, `--verbose`, `--timeout`,
  `--max-concurrency`.
- The non-flag behaviors `scan` had and `check` lacked: permission overrides
  through `OverrideApplier`, the policy egress allowlist merged with CLI hosts,
  per-server policy allowlists, and detector pin files.
- The fleet connection mode `check --connect-all` (decision
  [Q5](#q5-fleet-connections-in-check)). It conflicts with `--connect`,
  `--server`, and `--skip-connect`; it includes project-scope servers only with
  `--connect-project-configs`; and it uses the existing `--max-concurrency`,
  per-session `--timeout`, and large-fleet CLI sharding.
- Hidden compatibility flags `--skip-connect` and `--config-only`, which keep
  their safety constraints. `--skip-connect` is rejected together with
  `--connect` or `--connect-all`. `--config-only` requires `--config` and is
  rejected together with `--include-discovered`. Both are usage errors (exit 2).

Static `check` stays the default; nothing added in 2.12 runs unless asked for.

Flag mapping for the translation notice and the migration guide. Every
discovering `scan` form maps to `check --include-discovered`:

| `scan` (2.x) | `check` (2.12 and 3.0) | 3.0 interceptor |
| --- | --- | --- |
| bare `scan` (discovers and connects to every workstation server) | `check --include-discovered --connect-all` | Exit 2 naming the replacement: static `check` would lose connected coverage |
| `scan --skip-connect` | `check --include-discovered` | Runs if the same server set is selected |
| `scan --skip-connect --inject-check` (the 2.11 pre-commit hook) | `check --include-discovered --inject-check` | Runs if the same server set is selected |
| `scan --config FILE --config-only --skip-connect` | `check --config FILE` | Runs; narrowed to the named file by request (an exact translation also needs an explicit `--override-config`) |
| `scan --config FILE --config-only` without `--skip-connect` | `check --config FILE` plus an explicit connection selection | Exit 2: `--config-only` limits discovery, not connections |
| `scan --config FILE --skip-connect` (no `--config-only`) | `check --config FILE --include-discovered` | Known narrowing: `scan` appends explicit sources and `check` deduplicates them, so overlapping sources can be lost; exit 2 unless the same server set is proven |
| `scan --clients NAME` | `--client NAME` | Same flag mapping |
| `scan --clients a,b` | `--client a --client b` | Exit 2 naming repeated `--client`: comma-separated selections are untranslatable |
| `scan --json PATH` | `--output-json PATH` (`--json` alone writes stdout) | Exit 2 naming `--output-json PATH` |
| `scan --connect-project-configs` (connected) | `check --include-discovered --connect-all --connect-project-configs` | Exit 2: requires an explicit `check` connection selection |
| every other flag in the table | same flag | Same flag mapping |

The 3.0 interceptor follows two rules:

1. **Preserved coverage runs the mapped command.** An invocation whose
   coverage is preserved runs the mapped `check` command, with one stderr line
   showing the translation. That line does not claim exact source coverage: it
   names `check`'s source acceptance limits (a 1,000-server cap per source and
   across accepted sources, a 1,048,576-byte source limit, nesting depth 64,
   20,000 containers, and symlink refusal for discovered sources). Discovered
   sources rejected by those limits emit `review_source_skipped` on stderr and
   in JSON and SARIF reports.
2. **Silent coverage loss or untranslatable input exits 2 naming the
   replacement.** Coverage preservation takes precedence: any lost source or
   lost connected coverage goes to this rule. That covers bare `scan`, `scan`
   without `--skip-connect`, any spelling the table cannot translate exactly
   (`--json PATH`, `--clients a,b`), any option absent from the frozen table,
   and any discovery shape `check` cannot express. Untranslatable arguments
   fail closed; they are never guessed.

Classification uses parsed options only, never running both discoveries. A
translation counts as preserved only if it selects the same server set;
`--config-only` may narrow to the named file. The classifier reports three
outcomes, `preserved`, `narrowed` (explicit `--config-only`), and
`would-silently-shrink`. In 2.12 it treated some discovery shapes as possible
silent shrinkage: Claude Code discovery can include other project scopes that
`check` cannot select, and `check` adds Cursor project discovery. Under the
2.12 behavior, unfiltered discovering forms, including the 2.11 pre-commit
hook command, reported no exact translation even though their mapping target
is `check --include-discovered`. With D22 built, unfiltered static forms are
exact through the opt-in `--scan-compatible-sources` selector, which
reproduces `scan`'s source selection: the translation appends it after
`--include-discovered`, and synthetic parity tests prove the result against
unchanged library discovery. Plain `check` retains its stricter,
superset-safe behavior. A config-only `scan` without `--override-config` still
reports no exact translation, and D22 does not change that, because `scan`
reads the default overrides in that mode and `check` does not.

Deprecation messaging:

- 2.12 (shipped): every `scan` run prints one stderr line before work starts.
  It is either the exact `check` translation with the source-limit statement
  above, or `scan: no exact check translation exists:` followed by the reasons.
  It goes to stderr so JSON and SARIF files and stdout stay unchanged, and it
  never changes the exit code.
- 2.12 (shipped in 2.12.0, C-4): a zero-source `check` run gets an additive
  `no_sources_reviewed` warning. In 3.0 it stays a warning with the exit code
  unchanged (decision [O-1](#o-1-zero-source-check-in-30)).
- 3.0: `scan` applies the two rules above.

`ScanOptions` and `engine.run_scan` keep their 2.x defaults in 3.0 (discover
and connect), so library callers see no behavior change from the CLI change.
The MCP server tool names exposed by `serve`, including `scan_mcp_servers`,
are unchanged. The default reach of `scan_mcp_servers` changes in 3.0
(decision [D20](#d20-serve-tool-reach-in-30)): 2.12 added a `connect` argument
(default `true` in 2.x) and announced the change in the tool description, and
3.0 defaults to a static audit that connects only with `connect=true`.
`skip_connect=true` continues to disable connections. The other `serve` tools
keep their 2.x reach, and each description states it (decision
[O-2](#o-2-reach-of-the-other-serve-tools)).

### `monitor` deletion

`monitor` has been hidden and deprecated since 2.9 and cannot proxy a real MCP
stdio server: it frames with `Content-Length` headers instead of
newline-delimited JSON-RPC. 3.0 deletes `src/mcp_audit/monitor.py`, its registry
entry, and `tests/test_monitor.py`. An invocation of `mcp-audit monitor`
reports an unknown command. There is no replacement proxy (an enforcing proxy
is out of scope). The nearest supported workflows are `shadow` for read-only
review of saved pins and tool surfaces, `watch` for config changes, and
`check --pin-check` (2.12) for drift.

### `_run_scan_core` deletion

`mcp_audit._core_cli._run_scan_core` is a frozen wrapper that builds
`ScanOptions` and calls `engine.run_scan` with the CLI console. It has emitted
`DeprecationWarning` since 2.3. No code in this repository calls it outside
tests; the documented external caller is a downstream shadow-mcp integration.

3.0 deletes `_run_scan_core` and the `mcp_audit.cli.__getattr__` shim that
also re-exports `_run_scan` and `_parse_clients`. Callers move to:

```python
from mcp_audit.engine import ScanOptions, run_scan

report = await run_scan(ScanOptions(skip_connect=True, pin_check=True), servers=servers)
```

`run_scan` accepts `servers`, `parse_errors`, `config_paths`,
`override_applier`, `console`, and `pin_store` keyword arguments, so every
`_run_scan_core` argument has a direct equivalent. In 2.12, `_parse_clients`
moved to `mcp_audit.client_filter`, `watcher.py` imports it from there, and
the `mcp_audit.cli` shim emits `DeprecationWarning` for `_run_scan` and
`_parse_clients` naming their new homes. Under the Q4 interceptor,
`scan_cli._run_scan` and the legacy `scan` engine path in `_core_cli.py` are
deleted with it; `scan` keeps only its option parsing and the translation
table.

### Hidden 2.x aliases

The hidden lab topic aliases, `safeforge-preinstall`, `safeforge-run`, and
`skillscan` were promised "through 2.x" and are removed in 3.0. The `pin`
alias for `baseline pin` is the exception decided in
[Q7](#q7-hidden-2x-aliases): it appears in the D19 migration command, in every
pin warning, and in `examples/ci/pin-stale-review.yml`, so it stays
permanently. Since 2.12, every use of the other hidden aliases prints a stderr
notice naming the namespaced replacement; `pin` is exempt from that notice.
Making `pin` a visible, documented alias in help shipped in 2.12.0 (I-2).

## 5. v1 pin removal (D19)

D19 is approved: 2.11 warns on every v1 pin read with the `pin --refresh`
migration command, and 3.0 removes v1 support. Decision
[Q6](#q6-reading-a-v1-pin-in-30) fixes how 3.0 reads a v1 entry: never a
pass.

### 3.0 behavior when a v1 entry is read

Building on the existing withheld-baseline path in `engine.py`:

- **Withheld whether or not trusted keys exist.** A genuine v1 server entry
  (`_is_legacy_entry`) is never compared. It is withheld for every pin-based
  check (`--pin-check`, `--canary-check`, `--escalation-check`,
  `--provenance-check`, `--integrity-check`, `--verify-artifacts`,
  `--download-artifacts`), with a `pin_baseline_withheld` warning that names
  the server and the migration command. In 2.x a v1 entry is withheld only
  when trusted pin keys exist.
- **The keyless case is a break.** A keyless 2.x install still compares v1
  entries. In 3.0 that comparison stops and the entry is withheld like any
  other; section 6 lists this as a breaking change.
- **Requested pin checks fail.** A requested pin check whose baseline is
  withheld fails the run. 3.0 turns on by default the behavior that 2.12
  shipped as the opt-in policy boolean `fail_on.pin_baseline_withheld`
  (default `false` in 2.x). Section 8 records the
  [implementation details](#pin-failure-details): all seven pin-dependent
  checks, exit 2 after reports, and `watch` under O-3.
- **Partial machine-readable coverage.** Coverage for an affected check is
  incomplete, never a pass: `coverage.pin_check.state` is `partial` with
  reason `pin_baseline_withheld`, even if every baseline was withheld or
  connections were disabled. 2.12 already reports this for withheld baselines,
  and a withheld canary baseline marks `runtime_security` coverage as partial.
- **Mixed-row exclusion.** In a mixed entry, v2 rows compare as today. v1 rows
  are dropped from comparison and listed in the warning as uncovered tools,
  the same way canary comparison treats `uncovered_legacy_tools` today. Those
  names are excluded from both saved and current inventories before
  calculating `NEW`/`REMOVED`, so an uncovered v1 row cannot become artificial
  drift. The 3.0 implementation also excludes them from `CHANGED`. The
  exclusion is 3.0 only; 2.x retains v1 drift and refresh comparisons.
- `_legacy_tool_hash`, `canonical_json_bytes(..., legacy=True)`, the
  `review_unverified_legacy` refresh path, and the v1 branches in key rotation
  are deleted. 3.0 `pin --refresh` does not hash v1 entries.
- The pin file is never rewritten on read. Only an explicit refresh replaces a
  v1 entry.

### Migration path

1. Before upgrading, on 2.11 or 2.12, run
   `mcp-audit baseline pin --refresh SERVER` to review the diff against the v1
   baseline, then `--apply`. This is the last release line that can show a
   diff against a v1 hash.
2. After upgrading, a remaining v1 entry has no comparable baseline.
   `baseline pin --refresh SERVER` shows the full current surface for review as
   if the server were newly pinned, then `--apply` writes a v2 entry (signed
   when a trusted key is configured).

Detection before upgrade: the 2.11 warning on every v1 read in terminal output
and in the JSON `warnings` array, plus the existing `pin_schema_outdated`
warning. Since 2.12 the warning text names the refresh command and states that
3.0 withholds v1 baselines even without trusted keys. Opting in to
`fail_on.pin_baseline_withheld: true` on 2.12 previews the 3.0 failure.

### GitHub Action `args` contract

Since 2.12 the Action chooses its command grammar by installed capability, not
by major version. It probes `mcp-audit check --help` for the expanded `check`
options (`--include-discovered`, `--output-json`, `--inject-check`,
`--connect-all`). An install without them, which includes every package below
2.12, keeps the legacy `scan` arguments. 2.12 and newer, including 3.x, get
`check` arguments. Free-form `args` follows the selected grammar. Under
`check`, legacy-only spellings are translated with a notice that logs the
translated command (`--json PATH` and `--json=PATH` become `--output-json
PATH`; a single `--clients NAME` becomes `--client NAME`), or rejected with exit
2 and the replacement named when no exact translation exists
(comma-separated `--clients a,b`). Hidden `--skip-connect` and `--config-only`
keep their `check` safety constraints, so with the default `skip-connect:
"true"` input, connection flags in `args` fail instead of overriding it. The
[CI guide](guides/ci.md#command-grammar-and-release-tags) documents the full
mapping. The pre-commit hook runs `mcp-audit check --include-discovered
--inject-check` since 2.12.

[Q8](#q8-how-core-finds-lab-commands)). `watch` without its optional
`watchfiles` dependency still exits 1 with the `mcp-audits[watch]` install
hint. The inconsistency is known and retained for compatibility.

## 8. Decisions (owner-approved, Oct 12 to Oct 31 2026)

The owner approved Q1 to Q9, D20, and D21 on Oct 12 2026 (PT). Eight reviewers
converged on Q1 to Q9 across two consultation rounds; D20 and D21 surfaced
during that review. D22 surfaced during 3.0 planning and was approved on
Oct 13 2026 (PT). O-1 to O-3 surfaced in the 3.0 implementation consultation
and were approved on Oct 14 2026 (PT); O-4 surfaced during review of the `scan`
interceptor and was approved on Oct 31 2026 (PT). Each entry keeps the options
considered and one line on why the chosen option won. The
[implementation details](#implementation-details-that-refined-the-decisions)
at the end of this section record where the build refined an approved
decision.

### Q1. What `mcp-audits` installs

- A. `mcp-audits` stays the core distribution; labs and Proof are separate
  distributions offered as extras (`[labs]`, `[proof]`, `[all]`).
- B. `mcp-audits` becomes a metapackage that installs all three; core is
  renamed (for example `mcp-audits-core`).
- C. `mcp-audits` is core plus Proof; only labs split out.

**Decided: A** (8 of 8). Condition: `uv tool` users must install
`mcp-audits-proof` directly to get `proof-before-action` on `PATH`, because an
extra does not expose its scripts, and every split-install notice says so.
Why: it keeps the package name, `server.json`, and `uvx mcp-audits serve`
meaning the review tool, and makes the default install the smaller surface.

### Q2. Proof Before Action's home

- A. A separate distribution in this repository and release train
  (`mcp-audits-proof`).
- B. A separate repository with its own release process.

**Decided: A** (8 of 8). Why: Proof already has no code dependency on core, so
a later move stays possible, while moving now would duplicate the release
gates in the same release that splits the package.

### Q3. Versioning

- A. Lockstep: all three distributions share one version and release together;
  cross-distribution requirements are exact pins.
- B. Independent versions with compatible ranges.

**Decided: A, with release safety** (8 of 8). Conditions: publication order is
core, then labs, then proof; no tag, GitHub Release, Registry entry, or Action
ref advances until every pinned wheel and sdist is published and verified; and
a documented recovery covers a partial publication (section 3). Why: labs
import core internals, which exact pins make safe, and the release tooling
already assumes one version.

### Q4. What `scan` means in 3.0

- A. Hidden alias of `check` with `check` grammar and static default;
  legacy-only spellings fail with the replacement named.
- B. Keep the legacy `scan` grammar unchanged as a hidden command through 3.x.
- C. Remove `scan`; `mcp-audit scan` prints the migration text and exits 2.

**Decided: a legacy interceptor that combines A and C.** Round 1 split (2 A,
4 A-modified, 2 C); in round 2 all eight accepted this shape. `scan` is a
frozen translation table over `scan`'s option names, not a bare alias and not
a second engine path. Conditions:

- Preserved coverage runs the mapped `check` command with one stderr notice
  that does not claim exact source coverage and names `check`'s source limits.
- Silent coverage loss or untranslatable input exits 2 and names the
  replacement `check` command. Coverage preservation takes precedence over
  option mapping.
- Every discovering form maps to `check --include-discovered`, including the
  2.11 pre-commit hook's `scan --skip-connect --inject-check`.
- `scan --config-only` limits discovery, not connections, so without
  `--skip-connect` it exits 2.
- Classification uses parsed options only, never running both discoveries,
  and a translation is preserved only if it selects the same server set
  (`--config-only` may narrow to the named file).
- `check` accepts `--skip-connect` and `--config-only` as hidden compatibility
  flags that keep their safety constraints.

Why: one grammar and one engine path, while existing invocations either keep
their coverage or fail with the exact fix, never with a silent reduction.
Section 4 has the mapping table and the 2.12 classifier's current behavior.

### Q5. Fleet connections in `check`

- A. Add an explicit fleet mode to `check` (`--connect-all`).
- B. Allow `--server` to repeat; no "all" mode.
- C. Drop fleet connections from the CLI; library callers keep
  `ScanOptions`.

**Decided: A, explicit and bounded** (8 of 8). Conditions: `--connect-all` is
distinct from `--connect` and mutually exclusive with `--connect` and
`--server`; it includes project-scope servers only with
`--connect-project-configs`; and it keeps canary's explicit-config
restriction, `--max-concurrency`, per-session `--timeout`, and CLI sharding.
Why: the Action's `skip-connect: false` input needs a fleet mode, and an
explicit flag keeps static as the default. Shipped in 2.12.

### Q6. Reading a v1 pin in 3.0

- A. Withhold the v1 server entry from every pin-based check with a
  `pin_baseline_withheld` warning and incomplete coverage; v2 rows in mixed
  entries still compare; v1 rows are listed as uncovered.
- B. Refuse the whole pin file with a pin file error (exit 1).
- C. Ignore v1 rows so their tools appear as `NEW` drift.

**Decided: A, never a pass** (8 of 8). Conditions: withheld whether or not
trusted keys exist; a requested pin check with a withheld baseline fails the
run; coverage is partial in machine-readable form; mixed v1 rows are excluded
from `NEW`/`REMOVED`; and the keyless case is listed as a break. 2.x
`pin --refresh` keeps the v1 diff, and 3.0 does not hash v1. Why: it never
passes silently and does not block review of other servers; B turns one stale
row into a total outage and C buries the cause under drift. Section 5 has the
details.

### Q7. Hidden 2.x aliases

- A. Remove every hidden alias in 3.0.
- B. Remove the lab topic, SafeForge, and `skillscan` aliases; keep `pin` as a
  permanent alias of `baseline pin`.
- C. Keep all hidden aliases through 3.x.

**Decided: B, with `pin` promoted** (8 of 8). Conditions: a stderr notice on
every use of the removed aliases in 2.12 (shipped), and `pin` becomes a
visible, documented alias (shipped in 2.12.0, I-2). Why: `pin` appears in the
D19 migration command and every pin remediation string, so removing it would
break the migration instructions themselves.

### Q8. How core finds lab commands

- A. Core keeps the static lab registry and imports `mcp_audit_labs` modules
  only when a lab command runs; a missing labs distribution exits 2 with the
  install command.
- B. Labs register commands through an entry point group that core reads.
- C. Labs ship their own console script and core drops the `lab` namespace.

**Decided: A, with a narrow guard** (8 of 8). Conditions: the guard applies to
SafeForge and `lab --conformance-probe` too, and only a missing module whose
top-level name is `mcp_audit_labs` or `proof_before_action` produces the
install hint and exit 2; any other `ImportError` propagates, including missing
transitive dependencies. Why: it reuses the lazy-import pattern of the
optional extras and avoids starting a plugin mechanism. The guard shipped in
2.12. `watch` keeps exit 1 for its missing optional dependency, recorded as a
known quirk in section 6.

### Q9. 2.x support after 3.0

- A. Security fixes on 2.x for a fixed window after 3.0.0, no features.
- B. No 2.x releases after 3.0.0.

**Decided: A, 120 days.** Round 1 had seven votes for 90 days and one for 180;
all eight accepted 120 days in round 2. Conditions: the end date is published
in the 3.0.0 notes; a `release/2.x` branch carries its own release state,
checked by `verify_release.py`; and the notes name the backport surfaces: the
package, the Action, and the hook. Why: section 6 breaks touch CI workflows
that may not upgrade on release day, and a bounded window keeps security fixes
reachable without an open-ended branch.

### D20. `serve` tool reach in 3.0

`serve`'s `scan_mcp_servers` connects to every configured server by default in
2.x, while the 3.0 CLI is static by default.

- (a) Keep the current default; the tool stays inconsistent with the CLI.
- (b) In 3.0, `scan_mcp_servers` defaults to a static audit and connecting
  requires an explicit `connect=true` argument.
- (c) Split it into `review_mcp_servers` (static) and `scan_mcp_servers`
  (connected, explicit).

**Decided: (b).** 2.12 added the `connect` argument (default `true`) and states
the coming change in the tool description; `skip_connect=true` still disables
connections. Why: it matches the CLI, keeps one tool name for clients, and an
agent calling the tool sees the change a full minor release ahead.

### D21. Reserve the new PyPI names

**Decided and done.** The owner published `mcp-audits-labs` and
`mcp-audits-proof` 0.0.1 placeholders that only point at `mcp-audits`, so both
names are reserved on PyPI ahead of 2.12.

### D22. Exact source selection for translated static scans

- (a) Make `check --include-discovered` use `scan`'s source selection by
  default.
- (b) Add hidden `check --scan-compatible-sources` to opt into `scan`'s source
  selection; plain `check` keeps its stricter, superset-safe behavior.

**Decided: (b).** The selector requires `--include-discovered` and is rejected
with `--project`, `--config-only`, `--connect`, and `--connect-all`. It selects
every Claude Code `projects[*]` scope, excludes Cursor project files, and
includes cwd `.mcp.json` and `.vscode/mcp.json`. A malformed sibling Claude
project entry preserves `scan`'s whole-file loss behavior. A present file with
no server map yields an empty result, not a config-health diagnostic. Server
deduplication matches `scan` by `(name, client, config, project)`. Because
server identities omit the project path, the selector cannot be combined with
a connection selection.

Why: translated static forms can preserve `scan`'s source set when explicitly
requested, while the recommended plain `check` behavior remains superset-safe.

Status: built as the hidden `check --scan-compatible-sources` flag (D-1) and
parity-proven (D-2) before the 3.0 `scan` interceptor turned strict.
`scan --skip-connect`, the 2.11 hook form, and the other static discovering
forms translate exactly by appending the flag after `--include-discovered`,
and the parity tests compare each against unchanged library discovery. The
flag is supported for all of 3.x because the translation notice prints it.

### O-1. Zero-source `check` in 3.0

A `check` run that reviews no source gets the 2.12 `no_sources_reviewed`
warning.

- (a) Keep the `no_sources_reviewed` warning; the exit code is unchanged.
- (b) Fail such a run by default.
- (c) Keep the warning and add an opt-in policy gate.

**Decided: (a)** (8 of 8, Oct 14 2026 PT). Why: the Action and the hook run
`check --include-discovered` on runners that usually have no MCP configs, and
2.x never warned that this exit code would change; (c) can come in a 3.x
minor release.

### O-2. Reach of the other `serve` tools

D20 changes only the default reach of `scan_mcp_servers`.

- (a) The other tools keep their current reach, and each tool description
  states it accurately.
- (b) Every tool becomes static by default.

**Decided: (a)** (8 of 8, Oct 14 2026 PT). Eight tools connect by design:
`get_high_risk_servers`, `check_server`, and the injection, SSRF, trifecta,
shadowing, escalation, and provenance findings. Four are static toward MCP
servers: `list_discovered_servers` and the integrity, package-verify, and
artifact-verify findings; the last two contact package registries only. Tool
descriptions that run pin checks also state that a withheld baseline appears
as partial coverage, not as a failure. Why: only `scan_mcp_servers` carried a
2.12 notice of a default change, so changing the others would break agents
with no 2.x warning, and an accurate description lets an agent see the reach
before calling.

### O-3. `watch` with a withheld pin baseline

`watch` always runs the pin check and loads no policy.

- (A) Never exit for this: every loop writes reports with partial coverage and
  renders the warning.
- (B) Exit 2 after writing outputs on any scan with a withheld baseline.
- (C) Exit 2 on the initial scan only; rescans warn and continue.

**Decided: (A)** (4 A, 2 B, 2 C; Oct 14 2026 PT). Why: Q6 fails a *requested*
pin check and `watch`'s is implicit, and a v1 baseline lasts until it is
refreshed, so (B) and (C) would stop the watcher at startup for every user
with one old pin, with no 2.x warning that `watch` exits. The one-shot
commands carry the exit.

### O-4. Skipped discovered sources in compatibility SARIF

A discovered source refused by `check`'s source limits yields
`review_source_skipped` and a high `config_parse_failure` finding, and exits 0
without a `fail_on.config_health` policy. The default compatibility SARIF
profile reported it only as a tool execution notification.

- (a) Keep the notification only, documented as a known issue.
- (b) The compatibility profile also emits one warning-level result per
  skipped discovered source.
- (c) Set `executionSuccessful: false` when any discovered source is skipped.

**Decided: (b)** (Oct 31 2026 PT). Each result is an
`MCP-CH-CONFIG-PARSE-FAILURE` warning with its reason, source location, and
`--config FILE` remedy, including under translated static scans; exit codes,
the existing notifications, and extended-profile results are unchanged. Why:
reduced coverage becomes visible in code-scanning dashboards without changing
any exit code.

### Implementation details that refined the decisions

These details were settled while building 3.0 and matter to anyone relying on
the decisions above.

#### D22 selector rules

- The selector requires `--include-discovered`. It is rejected (usage error,
  exit 2) with `--config`, `--project`, `--config-only`, `--connect`, and
  `--connect-all`: `scan` appends an explicit file after discovery while
  `check` deduplicates it, and server identities omit the project path, so a
  connection selection would be ambiguous.
- Under the selector, `check` reproduces `scan`'s server selection exactly:
  every Claude Code `projects[*]` scope, no Cursor project file, cwd
  `.mcp.json` and `.vscode/mcp.json`, whole-file loss on a malformed sibling
  project entry, server-level deduplication by `(name, client, config,
  project)`, and an empty result for a present file with no server map.
  `check`'s config-health diagnostic would make coverage partial and could
  fail `fail_on.config_health`.
- Without the flag, `check`'s path and output are unchanged, and plain `check`
  stays the recommended spelling. `check`'s source acceptance limits still
  apply under the flag and are named in the translation notice.

#### Pin failure details

- The withheld-pin gate covers all seven pin-dependent checks: pin, canary,
  escalation, provenance, integrity, verify-artifacts, and download-artifacts.
  A requested check whose baseline is withheld fails the run with exit 2, the
  existing policy-gate code, after reports are rendered and written.
- It applies to `check` (and so to the `scan` interceptor) and to `shadow`.
  `watch` follows O-3. Library callers and library policy evaluation are
  unchanged.
- The gate is unconditional. An explicit `fail_on.pin_baseline_withheld:
  false` is accepted and ignored with a loader warning, never a schema error.
- `policy_result` carries the violation even without `--policy`, so JSON is
  never `null` alongside this exit 2.

#### Release tooling details

- A committed `release/distributions.json` lists the three distributions in
  publication order and must equal the release-controls copy byte for byte.
  Any 3.x version must use a three-distribution contract; a missing or
  unsplit contract fails closed.
- Releases are commit-first: `publish.yml` is dispatched with an approved
  `commit` and `version` and refuses an existing tag. The `v3.0.0` lightweight
  tag is created at the approved commit only after all six files are
  published and read back; there is no moving `v3` tag.
- Recovery from a partial publication is a workflow input. `resume=true`
  requires the original run ID, the approved manifest SHA-256, and the
  original control SHA. It downloads the retained bytes instead of rebuilding,
  skips build and smoke, stages only the files missing from PyPI, rejects
  yanked files, and stops on any digest mismatch. Release artifacts are kept
  for 90 days; expired artifacts mean a new patch version.
- `release/2.x` was cut from the 2.12.0 release commit. Its publish and
  Registry workflows are branch-local, because `workflow_dispatch` runs the
  workflow file at the dispatched ref: they accept only `release/2.x`, use the
  `pypi-2x` environment, verify with `--release-branch release/2.x`, and
  publish the single unsplit package. Main's workflows stay main-only.

## 9. Out of scope

- An enforcing proxy (D13b). `monitor` is deleted without a replacement and
  `shadow` stays read-only.
- `fix --write`. `fix` stays a dry run.
- A plugin or DAG framework, including third-party lab or detector
  registration.
- Hosted sharing of checkup cards.
- Retiring Proof Before Action v1 capsule, observation, and index schemas.
  They are a separate decision for the Proof distribution.
