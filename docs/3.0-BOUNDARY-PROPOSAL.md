# 3.0 Boundary Proposal

Status: proposal for owner sign-off. Nothing in this document changes 2.x
behavior. It records what a 3.0 release would remove, split, and rename, what
each change breaks for users, and which warnings 2.x ships first so that every
break is visible before an upgrade.

## 1. Summary and goals

MCPAudit 2.x ships one distribution, `mcp-audits`, that contains the static and
connected MCP review, eight offline labs, SafeForge, and the standalone Proof
Before Action CLI. It also carries compatibility surfaces that 2.x promised to
keep until 3.0: the legacy `scan` grammar, the hidden `monitor` proxy, the
frozen `mcp_audit.cli._run_scan_core` shim, hidden 2.x command aliases, and
legacy v1 pin entries.

The 3.0 boundary has four goals:

1. Make the default install the security review tool only. Labs and Proof
   Before Action keep their own release notes and threat models, and users who
   do not run them should not install their code or review their changes.
2. Make `check` the one review command. `check` already has the safe default
   (static, no connections) and the newer grammar; `scan` remains the older
   grammar with connect-everything as its default.
3. Delete the surfaces already announced for removal in 3.0: `monitor`
   (deprecated in 2.9), `_run_scan_core` (deprecated since 2.3, scheduled for
   3.0 in 2.10), and v1 pins (owner decision D19).
4. Give every break a 2.x warning, a migration command, and a way to detect it
   before upgrading.

Why now: the compatibility surfaces are each small, but together they keep two
CLI grammars, two pin hash contracts, and an unused proxy in the review path.
2.11 makes the v1 pin warning universal (D19), so 3.0 is the first release
where every announced removal has had a warning in a shipped release.

### CLI surface

`src/mcp_audit/_command_registry.py` defines the lazy registry:

- Everyday: `check`, `checkup`, `inspect`, `demo`, `explain`, `fix`.
- Integrations: `serve`, `shadow`.
- Advanced: `scan` ("Full legacy audit with explicit scan modes"), `discover`,
  `watch`, `baseline pin`, `skills scan`, `safeforge preinstall|run`.
- Labs: `lab` with eight topics, plus `lab --conformance-probe --url URL`.
- Hidden: `monitor` (deprecated, Click `deprecated=`), eight top-level lab topic
  aliases (`agent-ui`, `authorization-posture`, `cache-contract`,

  and `pin`. `docs/labs/README.md` documents these as hidden aliases "through
  2.x".

### `check` and `scan` today

`check` (`src/mcp_audit/check_cli.py`) reads an explicit `--config FILE` only,
or the fixed supported-client allowlist, statically. `--connect` connects to
exactly one identity selected with `--server CLIENT:SCOPE:NAME`. `--json`
writes JSON to stdout and `--output-json FILE` writes a file. `check` runs the
injection, trifecta, and shadowing detectors only when a card is requested on
a connected check, and exposes none of the other opt-in detectors.

`scan` (`src/mcp_audit/_core_cli.py`, implemented by `scan_cli._run_scan`)
discovers all supported configs and connects to every workstation server by
default. It has options that `check` lacks:

- Connection scope and budgets: `--skip-connect`, `--config-only`,
  `--connect-project-configs`, `--clients a,b`, `--timeout`,
  `--max-concurrency`.
- Opt-in detectors: `--inject-check`, `--ssrf-check`, `--ssrf-allowlist`,
  `--egress-check`, `--egress-allowlist`, `--multi-tenant-hosts`,
  `--pin-check`, `--trifecta-check`, `--shadow-check`, `--escalation-check`,
  `--provenance-check`, `--integrity-check`.
- Higher-reach modes: `--verify-artifacts`, `--download-artifacts`,
  `--llm-analysis`, `--canary-check`, `--canary-calls`,
  `--canary-identities`, `--canary-safe-tool`.
- Output: `--json PATH` (a path, so `--json -` writes a file named `-`),
  `--sarif-profile`, `--redact`, `--verbose`.

So `scan` cannot become an alias of `check` until `check` can express these
options. Section 4 covers that.

### Pins

`src/mcp_audit/pinning.py` writes `pin_schema: 2` entries hashed over
`mcpaudit.tool-surface.v2`, with an optional signed `mcpaudit.pin-manifest.v1`.
It still reads v1 entries: tool rows without `pin_schema` (default 1), hashed
by `_legacy_tool_hash` over name, description, and input schema with
`canonical_json_bytes(..., legacy=True)`. `_is_legacy_entry` identifies a
genuine v1 entry; mixed entries hold v2 rows plus retained v1 rows. Today a v1
entry warns `pin_schema_outdated` when the baseline is trusted, and is
withheld (`pin_baseline_withheld`) only when trusted pin keys exist. Canary
comparison drops v1 rows through `uncovered_legacy_tools`. In 2.11, item R-6
makes every v1 read warn with the `pin --refresh` migration command (D19).

## 3. Proposed package split

### Distributions

| Distribution | Import package | Console scripts | Contents |
| --- | --- | --- | --- |
| `mcp-audits` | `mcp_audit` | `mcp-audit`, `mcp-audits` | Core |
| `mcp-audits-labs` | `mcp_audit_labs` | none | Eight lab topics (including the enforcement fixture), conformance probe, SafeForge |
| `mcp-audits-proof` | `proof_before_action` | `proof-before-action` | Proof Before Action |

The new distribution names are working names; PyPI availability has not been
checked and must be confirmed before 3.0.

`mcp-audits` stays the core distribution under its current name (see
[question Q1](#q1-what-mcp-audits-installs)). It gains extras:

- `mcp-audits[labs]` installs `mcp-audits-labs` at the same version.
- `mcp-audits[proof]` installs `mcp-audits-proof` at the same version.
- `mcp-audits[all]` installs both, plus the existing `watch`, `llm`, and `otel`
  extras.

So `uv tool install mcp-audits` gives the review CLI, `serve`, `watch` (with
the `watch` extra), pins, policy, and all report formats. The umbrella install
that matches 2.x contents is `uv tool install 'mcp-audits[labs,proof]'`; because
`uv tool` exposes only the root package's scripts, Proof Before Action users
install it as its own tool with `uv tool install mcp-audits-proof`.

### Module assignment

- Core: the 75 core modules listed in section 2, minus `monitor.py`,
  `scan_cli.py` (if Q4 option A is chosen), and the `_run_scan_core` shim.
  Plus one new core module holding the OAuth URL helpers and limits that
  `probe.py` needs today from `authorization_posture_models.py`
  (`MAX_AUTHORIZATION_SERVERS`, `MAX_FETCHES`,
  `_expected_authorization_metadata_url`, `_expected_resource_metadata_url`,
  `_origin`, `_require_https_url`). The lab model re-imports them from core.
- Labs: the 34 lab and SafeForge modules listed in section 2, under
  `mcp_audit_labs`. SafeForge is a lab by evidence: its own threat model lives
  in `docs/labs/`, it targets a macOS Seatbelt research profile, and no user
  guide or Action recipe depends on it.
- Proof Before Action: the five `proof_*` modules under `proof_before_action`,
  with `__version__` read from its own distribution metadata instead of
  `mcp_audit`.

`skills scan` stays in core: it is an everyday review of local inputs, imports
only `redaction` and `__version__`, and is not documented as a lab.

### Dependency direction

```text
proof_before_action        (no MCPAudit imports)

mcp_audit_labs  ------>  mcp_audit (core)  ------>  third-party only
```

- Core imports nothing from labs or Proof Before Action. After the URL helper
  move, the only upward reference is the `lab` command registry, which names
  lab modules by string and imports them only when a lab command runs (see
  [Q8](#q8-how-core-finds-lab-commands)). That matches how core already treats
  the optional `watchfiles` and `anthropic` imports.
- Labs import core only through modules that are already shared today:
  `__version__`, `canonical`, `models`, `api`, `report`, `terminal_text`, the
  new OAuth URL module, and the `probe` request helpers. The `probe` helpers lose
  their leading underscore and are documented as internal-but-shared, safe
  because labs pin core to the exact same version.
- Proof Before Action imports nothing from core. It depends only on `click`,
  `pydantic`, and `pyyaml`.
- There are no import cycles. The extras on `mcp-audits` create a
  metadata-level loop (`mcp-audits[labs]` requires `mcp-audits-labs`, which
  requires `mcp-audits`); installers resolve this pattern routinely, and no
  code imports upward through it.

Third-party dependencies per distribution:

- Core: `click`, `rich`, `anyio`, `json5`, `mcp`, `cryptography`, `pydantic`,
  `pyyaml`, with optional `watch`, `llm`, `otel`.
- Labs: `mcp-audits==X.Y.Z`; the `mcp` SDK, `anyio`, `pydantic`, `click`, and
  `rich` arrive through core.
- Proof: `click`, `pydantic`, `pyyaml`.

### Shared contracts and their owners

| Contract | Owner | Rule in 3.0 |
| --- | --- | --- |
| `AuditReport` JSON (`schema_version` 1), `examples/schemas/audit-report.schema.json`, SARIF, HTML, checkup card | Core | Unchanged by the split. `docs/OUTPUT-CONTRACT.md` stays the core contract. |
| Pin file (`pin_schema` 2, `mcpaudit.tool-surface.v2`, `mcpaudit.pin-manifest.v1`) | Core | v1 entries no longer compared (section 5). v2 format unchanged. |
| Lab report and input schemas (`authorization-posture-*`, `oauth-transcript-*`, enforcement `mcpaudit.*.v1`, `mcpaudit.conformance-probe.v1`, `safeforge-manifest-v0`) | Labs | Unchanged; documented in `docs/labs/`. |
| Proof Before Action schemas (`proof-before-action.declaration.v1`, `observation.v1/v2`, `capsule.v1/v2`, `capsule-index.v1/v2`, `trust-manifest.v1`) | Proof | Unchanged. |
| Build provenance (`mcp-audits.build-provenance.v1`) | All three | Each wheel and sdist carries its own provenance file through the same build backend. |

A schema identifier never changes meaning when its module moves distribution.

### Installation and versioning

All three distributions release in lockstep from this repository with one
version number (see [Q3](#q3-versioning)). Labs pin `mcp-audits==X.Y.Z`
exactly; the extras on `mcp-audits` pin the other two exactly. One release
checklist run builds and verifies three wheels and three sdists;
`scripts/verify_release.py` grows one expected-scripts table per distribution,
and `docs/release-state.json` records the shared version. `server.json` keeps
`mcp-audits` with `serve`, so the MCP Registry identity does not change.

## 4. CLI changes

### `scan` becomes an alias of `check`

In 3.0, `check` is the primary name in help, docs, the Action, and the
pre-commit hook. `scan` is a hidden alias that invokes `check` with `check`
grammar and defaults (recommended option A in [Q4](#q4-what-scan-means-in-30)).

`check` must first be able to express what `scan` users run. 2.12 adds these
to `check`, additively:

- The opt-in detector flags, with the same names and meanings:
  `--inject-check`, `--ssrf-check`, `--ssrf-allowlist`, `--egress-check`,
  `--egress-allowlist`, `--multi-tenant-hosts`, `--pin-check`,
  `--trifecta-check`, `--shadow-check`, `--escalation-check`,
  `--provenance-check`, `--integrity-check`.
- The higher-reach modes with the same names: `--verify-artifacts`,
  `--download-artifacts`, `--llm-analysis`, and the `--canary-*` options.
- `--sarif-profile`, `--redact`, `--verbose`, `--timeout`,
  `--max-concurrency`.
- A fleet connection mode for users who connect to every server today (see
  [Q5](#q5-fleet-connections-in-check)).

Static `check` stays the default; nothing added in 2.12 runs unless asked for.

Flag mapping for the deprecation notice and the migration guide:

| `scan` (2.x) | `check` (2.12 and 3.0) |
| --- | --- |
| no connection flag (connects to every workstation server) | the Q5 fleet mode, for example `--connect-all` |
| `--skip-connect` | default; drop the flag |
| `--config FILE --config-only` | `--config FILE` |
| `--config FILE` without `--config-only` | `--config FILE --include-discovered` |
| `--clients a,b` | `--client a --client b` |
| `--json PATH` | `--output-json PATH` (`--json` alone writes stdout) |
| `--connect-project-configs` | the Q5 fleet mode with project scope included |
| every other flag | same flag |

Deprecation messaging:

- 2.12: every `scan` run prints one stderr line before work starts, for example
  `scan is deprecated and becomes an alias of check in 3.0; equivalent: mcp-audit check ...`,
  with the translated command built from the table above. It goes to stderr so
  JSON and SARIF files and stdout stay unchanged, and it never changes the
  exit code.
- 3.0: `scan` runs `check`. A legacy-only spelling is a usage error (exit 2)
  that names the replacement, never a silent reinterpretation. `scan --json PATH`
  already fails loudly under `check` grammar because `PATH` becomes an
  unexpected argument; the error text adds the `--output-json` hint.

`ScanOptions` and `engine.run_scan` keep their 2.x defaults in 3.0 (discover
and connect), so library callers see no behavior change from the CLI rename.
The MCP server tool names exposed by `serve`, including `scan_mcp_servers`,
are unchanged.

### `monitor` deletion

`monitor` has been hidden and deprecated since 2.9 and cannot proxy a real MCP
stdio server: it frames with `Content-Length` headers instead of
newline-delimited JSON-RPC. 3.0 deletes `src/mcp_audit/monitor.py`, its registry
entry, and `tests/test_monitor.py`. An invocation of `mcp-audit monitor`
reports an unknown command. There is no replacement proxy (an enforcing proxy
is out of scope). The nearest supported workflows are `shadow` for read-only
review of saved pins and tool surfaces, `watch` for config changes, and
`check --pin-check` (2.12) for drift.

### `_run_scan_core` deletion

`mcp_audit._core_cli._run_scan_core` is a frozen wrapper that builds
`ScanOptions` and calls `engine.run_scan` with the CLI console. It has emitted
`DeprecationWarning` since 2.3. No code in this repository calls it outside
tests; the documented external caller is a downstream shadow-mcp integration.

3.0 deletes `_run_scan_core` and the `mcp_audit.cli.__getattr__` shim that
also re-exports `_run_scan` and `_parse_clients`. Callers move to:

```python
from mcp_audit.engine import ScanOptions, run_scan

report = await run_scan(ScanOptions(skip_connect=True, pin_check=True), servers=servers)
```

`run_scan` accepts `servers`, `parse_errors`, `config_paths`,
`override_applier`, `console`, and `pin_store` keyword arguments, so every
`_run_scan_core` argument has a direct equivalent. `watcher.py` switches its
`_parse_clients` import to the module that owns it. If Q4 option A is chosen,
`scan_cli._run_scan` and the `scan` option block in `_core_cli.py` are deleted
with it.

### Hidden 2.x aliases

The hidden lab topic aliases, `safeforge-preinstall`, `safeforge-run`, and
`skillscan` were promised "through 2.x" and are removed in 3.0. The `pin`
alias for `baseline pin` is the exception proposed in
[Q7](#q7-hidden-2x-aliases): it appears in the D19 migration command, in every
pin warning, and in `examples/ci/pin-stale-review.yml`.

## 5. v1 pin removal (D19)

D19 is approved: 2.11 warns on every v1 pin read with the `pin --refresh`
migration command, and 3.0 removes v1 support.

### 3.0 behavior when a v1 entry is read

Recommended ([Q6](#q6-reading-a-v1-pin-in-30)), building on the existing
withheld-baseline path in `engine.py`:

- A genuine v1 server entry (`_is_legacy_entry`) is never compared. It is
  withheld for every pin-based check (`--pin-check`, `--canary-check`,
  `--escalation-check`, `--provenance-check`, `--integrity-check`,
  `--verify-artifacts`, `--download-artifacts`) whether or not trusted keys
  exist, with a `pin_baseline_withheld` warning that names the server and the
  migration command. Coverage for those checks on that server is reported as
  incomplete, never as a pass.
- In a mixed entry, v2 rows compare as today. v1 rows are dropped from
  comparison and listed in the warning as uncovered tools, the same way canary
  comparison treats `uncovered_legacy_tools` today.
- `_legacy_tool_hash`, `canonical_json_bytes(..., legacy=True)`, the
  `review_unverified_legacy` refresh path, and the v1 branches in key rotation
  are deleted.
- The pin file is never rewritten on read. Only an explicit refresh replaces a
  v1 entry.

### Migration path

1. Before upgrading, on 2.11 or 2.12, run
   `mcp-audit baseline pin --refresh SERVER` to review the diff against the v1
   baseline, then `--apply`. This is the last release line that can show a
   diff against a v1 hash.
2. After upgrading, a remaining v1 entry has no comparable baseline.
   `baseline pin --refresh SERVER` shows the full current surface for review as
   if the server were newly pinned, then `--apply` writes a v2 entry (signed
   when a trusted key is configured).

Detection before upgrade: the 2.11 warning on every v1 read in terminal output
and in the JSON `warnings` array, plus the existing `pin_schema_outdated`
warning.

output, the v2 pin format, signed pin manifests, policy files, override files,
`serve` and its MCP tool names, the `mcp-audits` package name, the
`mcp-audit` and `mcp-audits` scripts, and the `ScanOptions` library defaults.

## 8. Open design questions for the owner

### Q1. What `mcp-audits` installs

- A. `mcp-audits` stays the core distribution; labs and Proof are separate
  distributions offered as extras (`[labs]`, `[proof]`, `[all]`).
- B. `mcp-audits` becomes a metapackage that installs all three; core is
  renamed (for example `mcp-audits-core`). The metapackage must redeclare the
  `mcp-audit` and `mcp-audits` scripts because `uv tool` exposes only the root
  package's scripts, so the core and the metapackage both own those names.
- C. `mcp-audits` is core plus Proof; only labs split out.

Recommendation: A. It keeps the package name, `server.json`, the Action's
`pip install mcp-audits==X.Y.Z`, and `uvx mcp-audits serve` meaning the review
tool, and it is the only option where the default install is the smaller
surface the split is for. B keeps 2.x install contents but adds a script
ownership conflict and a rename; C keeps an unrelated tool in the default
install.

### Q2. Proof Before Action's home

- A. A separate distribution in this repository and release train
  (`mcp-audits-proof`).
- B. A separate repository with its own release process.

Recommendation: A for 3.0. It already has no code dependency on core, so a
later move to its own repository stays possible, but moving it now would
duplicate the release checklist, provenance backend, and supply-chain gates in
the same release that splits the package.

### Q3. Versioning

- A. Lockstep: all three distributions share one version and release together;
  cross-distribution requirements are exact pins.
- B. Independent versions with compatible ranges.

Recommendation: A. Labs import core internals (the `probe` helpers, models),
which exact pins make safe, and the release tooling already assumes one
version in `docs/release-state.json`. Revisit B only if Proof moves to its own
repository.

### Q4. What `scan` means in 3.0

- A. Hidden alias of `check` with `check` grammar and static default;
  legacy-only spellings fail with the replacement named.
- B. Keep the legacy `scan` grammar unchanged as a hidden command through 3.x.
- C. Remove `scan`; `mcp-audit scan` prints the migration text and exits 2.

Recommendation: A. It gives one grammar and one code path (`scan_cli.py` and
the `_core_cli.scan` option block go away) while existing invocations either
work or fail with the exact fix. B keeps two grammars and the
connect-by-default path; C breaks muscle memory for no extra safety.

### Q5. Fleet connections in `check`

Today `check --connect` requires exactly one `--server`. `scan` connects to
every workstation server by default.

- A. Add an explicit fleet mode to `check` (for example `--connect-all`, with
  `--max-concurrency` and `--timeout`), including project-scope servers only
  with the existing project consent wording.
- B. Allow `--server` to repeat; no "all" mode.
- C. Drop fleet connections from the CLI; library callers keep
  `ScanOptions`.

Recommendation: A. The capability exists and the Action's `skip-connect: false`
input depends on it. Making it an explicit flag keeps static as the default
while giving connected users a one-flag migration. B is safer for ad hoc use
but makes the Action enumerate identities it cannot know in advance.

### Q6. Reading a v1 pin in 3.0

- A. Withhold the v1 server entry from every pin-based check with a
  `pin_baseline_withheld` warning and incomplete coverage; v2 rows in mixed
  entries still compare; v1 rows are listed as uncovered.
- B. Refuse the whole pin file with a pin file error (exit 1).
- C. Ignore v1 rows so their tools appear as `NEW` drift.

Recommendation: A. It reuses the withheld path that already exists for
unauthenticated v1 entries when trusted keys exist, never passes silently, and
does not block review of other servers. B turns one stale row into a total
outage; C buries the cause under drift findings.

A related sub-question: should 3.0 `pin --refresh` still diff against a v1
hash for review? Recommendation: no. D19 removes v1 support, and two minor
releases of warnings give users a window to refresh with the diff on 2.x.

### Q7. Hidden 2.x aliases

- A. Remove every hidden alias in 3.0.
- B. Remove the lab topic, SafeForge, and `skillscan` aliases; keep `pin` as a
  permanent alias of `baseline pin`.
- C. Keep all hidden aliases through 3.x.

Recommendation: B. `pin` is in the D19 migration command, the pin warning and
remediation strings in `pinning.py`, and the CI examples; removing it in the
same release that forces a pin refresh would break the migration instructions
themselves. The others are low-traffic and already route through namespaced
commands.

### Q8. How core finds lab commands

- A. Core keeps the static lab registry (names and help text) and imports
  `mcp_audit_labs` modules only when a lab command runs; if the labs
  distribution is missing, the command exits 2 with the install command.
- B. Labs register commands through an entry point group that core reads.
- C. Labs ship their own console script (for example `mcp-audit-lab`) and core
  drops the `lab` namespace.

Recommendation: A. It is the pattern core already uses for the `watch`, `llm`,
and `otel` extras, keeps `mcp-audit lab --help` and shell completion working
without imports, and avoids starting a plugin mechanism, which is out of scope.

The 2.12 guard groundwork checks the missing import's top-level module name:
only `mcp_audit_labs` and `proof_before_action` produce an install hint and exit
2. Other `ImportError` exceptions propagate, including missing transitive
dependencies. SafeForge and `lab --conformance-probe` use the same lazy import
guard. `watch` still exits 1 when its optional dependency is missing; this is a
known exit-code inconsistency, retained for compatibility.

### Q9. 2.x support after 3.0

- A. Security fixes on 2.x for a fixed window after 3.0.0 (for example 90
  days), no features.
- B. No 2.x releases after 3.0.0.

Recommendation: A with a 90-day window. The breaks in section 6 touch CI
workflows that may not upgrade on release day, and a bounded window keeps
redaction and supply-chain fixes reachable without an open-ended branch.

## 9. Out of scope

- An enforcing proxy (D13b). `monitor` is deleted without a replacement and
  `shadow` stays read-only.
- `fix --write`. `fix` stays a dry run.
- A plugin or DAG framework, including third-party lab or detector
  registration.
- Hosted sharing of checkup cards.
- Implementing the split. This proposal changes no code, and the 2.12 items in
  section 7 are proposals until the owner signs off.
- Retiring Proof Before Action v1 capsule, observation, and index schemas.
  They are a separate decision for the Proof distribution.
