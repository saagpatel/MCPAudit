# MCPAudit 2.9.0 Candidate

Release status: candidate
Publication decision: NO-GO

MCPAudit 2.9.0 is a candidate for review and CI validation only. This source
state does not authorize tagging, publication, Registry mutation, deployment,
or claims of downstream adoption. Merging this candidate does not authorize
the release-state flip, which belongs in a separate reviewed PR.

## Upgrade notes

- Static instruction-text phrase matches are MEDIUM `INSTRUCTION_SHAPED_TEXT`,
  never HIGH on their own. HIGH injection policy gates no longer fail on
  phrases alone (D4); review thresholds if you relied on that behavior.
- Honest `readOnlyHint` tools no longer score `file_read` solely from that hint.
  Missing hints become one per-server FYI, with SARIF `MCP005` at `note`;
  genuine capability rows retain compatibility alert levels (D3).
  See [Scoring migration](SCORING-MIGRATION.md) before comparing scores or alerts.
- New `check`, `inspect`, `demo`, `explain`, and `checkup` commands support
  static review. Bare `mcp-audit` runs a static check; legacy `scan` grammar is
  unchanged. Use explicit connection options when a connected review is intended.
- Project-scope (cwd) configs are discovered but not connected without
  `--connect-project-configs` (D1). Review project commands and endpoints before opting in.
- After `pin keygen` or `pin trust-key --add`, unsigned v2 pins and pin files
  without a signed manifest report `MCP027`. Re-pin with `pin`, use
  `pin rotate-key --resign`, or use `pin --clear SERVER` then re-pin after
  review. Legacy v1 pins warn and their drift baseline is withheld while
  trusted keys exist.
- Stderr lines containing terminal control sequences are withheld from reports
  and `connection_error`; expect a withheld-line marker instead of that evidence.
- Unusual but legal `WWW-Authenticate` shapes, such as Basic and Bearer on
  separate header lines, produce an authorization-probe coverage warning
  instead of a metadata review. Review incomplete coverage before relying on a clean result.
- Account for new rule IDs `MCP044`–`MCP050` (protocol observations),
  `MCP051`–`MCP054` (static schema rules), `MCP027` (pin integrity), and
  `MCPAUTH` rules in downstream filters and policies.

## Known issues

- Credential redaction is pattern-based: a quoted secret flag value containing
  an escaped quote can leak its suffix; a zero-width character inside a
  bearer/basic token can leave its tail. Secret-shaped schema property names
  are not redacted, and terminal output prints tool names without credential
  redaction (terminal controls are still sanitized). A structural redaction
  redesign is planned for 2.10. Review field reports before sharing.
- A fresh CI trust store has no rollback high-water mark until its first
  verification, so restoring a complete older signed pin file in a one-shot
  CI job is not detected. Persist the trust store. Deleting it removes trusted
  keys and signing expectations; expectations are keyed by server name across
  pin files.
- Static schema header checks do not follow every composition form. Unsupported
  or ambiguous cases report incomplete coverage rather than findings.
- Legacy v1 pins do not cover annotation-only changes, title, output schema,
  icons, or metadata. Review `pin --refresh` before upgrading to v2; current
  v2 pins cover these fields, including security-relevant annotation deltas.

## Included capability groups

- Structural metadata signals and safe defaults retain phrase matches as
  experimental MEDIUM heuristics, expose obfuscated or hidden instruction
  evidence, and preserve keyword capability evidence despite contradictory hints.
- Terminal and offline HTML reports lead with summaries, suggested actions,
  and a coverage-qualified grade or Preview. Numeric risk scores and the JSON
  schema version retain their separate meanings; a grade is not a safety certificate.
- Plain-English findings, offline `explain`, and the finding reference describe
  consequences, repair steps, and confidence limits.
- A local counts-only `checkup` card is shareable without server names by
  default. Suppression preserves evidence and scores while showing visible
  counts and reasons; policies may forbid exceptions.
- Ed25519 signed pins include a signed document manifest, separate trusted
  public keys, rotation, integrity gates, and rollback warnings. Verification
  does not require a private key; legacy-v1 limitations remain visible.
- Protocol observation rules `MCP044`–`MCP050` retain observed versions,
  session-ID presence, cache hints, and tool order, with incomplete evidence
  separate from findings.
- A credential-free HTTP authorization probe records bounded `server/discover`
  evidence and reviews eligible public authorization metadata using bounded,
  address-pinned HTTPS requests. `MCPAUTH` rules do not prove a completed OAuth flow.
- Static schema rules `MCP051`–`MCP054` inspect header declarations, credential
  parameters, external references, and icon sources without fetching schemas or icons.
- Bounded stdio/HTTP transport and process hygiene cover frames, response bodies,
  listing/text budgets, session deadlines, concurrency, orphan process groups,
  and fail-closed stderr evidence.
- A lazy command registry adds the `lab` namespace and organized command
  families while preserving hidden legacy 2.x aliases. `monitor` is hidden
  and deprecated for removal in 3.0; this does not repair its proxy framing.
- Supply-chain hygiene retains security dependency floors, bounded advisory
  checks with explicit unavailable-feed failure, Action package-version binding,
  and exact wheel/sdist manifests and protected publication gates.

## Published-version boundary and rollback

The published version remains 2.8.1. `server.json`, Action examples, and
pre-commit examples continue to name that published package/tag. Retain
`mcp-audits==2.8.1` as the rollback pin and verify installed command identity
after rollback. Source metadata alone is not publication readback.

## Compatibility and required closure

The distribution remains `mcp-audits`; installed commands remain `mcp-audit`,
`mcp-audits`, and `proof-before-action`. Python 3.11–3.13 and the MCP SDK range
`mcp>=2.2.0,<3.0` remain supported. Existing 2.x report contracts remain
additive, with `schema_version` unchanged.

Before publication, land the reviewed candidate with exact-head CI and
security review, build and verify wheel/sdist artifacts from the final clean
revision, and promote release-state metadata in a separately reviewed PR.
Tagging and publishing need separate approval naming the exact release commit
and tag; independently read back PyPI, GitHub Release, and MCP Registry state.

Local tests and repository consistency establish only the behavior exercised
and candidate metadata consistency. They do not establish publication, live
third-party interoperability, deployment, adoption, or human outcomes. A clean
canary describes only its bounded in-session exercise.
