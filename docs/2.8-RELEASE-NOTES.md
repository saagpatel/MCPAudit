# MCPAudit 2.8.0 Candidate

Release status: candidate
Publication decision: NO-GO

MCPAudit 2.8.0 is the candidate for the opt-in runtime rug-pull canary and the
MCP SDK 2 migration. This source state supports review and CI validation only;
it does not authorize tagging, publication, Registry mutation, deployment, or
claims of downstream adoption.

## Included capability groups

- Opt-in runtime rug-pull canary (`scan --canary-check`, explicit isolated
  config only). It captures an in-memory surface baseline, makes a bounded
  number of empty-argument calls to safe-probe-eligible tools in the same
  session, and re-lists tools, prompts, and resources after every call.
  Mid-session surface changes are HIGH drift findings.
- Runtime tool-result and rendered prompt-body scanning for instruction
  overrides, credential hunts named by concrete secret target, and directions
  to call other tools. These are experimental MEDIUM heuristics (SARIF
  `MCP008`, description prefix `Experimental heuristic:`) and never fail a HIGH
  policy gate on their own. Result excerpts are withheld.
- Bounded probing: pagination capped at 20 pages per capture, scanned text
  capped at 64 KB per result with a coverage warning, `--canary-calls` bounded
  to 1-100 per server, and incomplete-coverage warnings for errors, timeouts,
  page-limit exhaustion, skipped required-argument prompts, truncation, and a
  lack of eligible tools.
- Served-but-unadvertised prompts and resources remain in canary scans, so
  enabling the canary never removes static checks.
- Explicitly configured legacy SSE servers route through the MCP SSE transport,
  and `check_server` connects only to a uniquely discovered exact-name match.

## Compatibility and package identity

- The distribution remains `mcp-audits`.
- Installed commands remain `mcp-audit`, `mcp-audits`, and
  `proof-before-action`.
- Python 3.11, 3.12, and 3.13 remain supported.
- The supported MCP dependency becomes `mcp>=2.2.0,<3.0`; MCP SDK 1.x is no
  longer supported. The 2.2.0 floor carries the fix for advisory
  GHSA-rwrf-2pqf-9j8j and also covers GHSA-qx49-fqc8-xw99 and
  GHSA-84m7-p3x7-pcfv.
- The connector uses the MCP 2 `Client` API, the in-process server uses
  `MCPServer`, and the connected stdio fixture uses the MCP 2 low-level server
  handler contract.
- Public CLI command names, MCP tool names, report fields, structured tool
  results, and the no-inherited-environment spawn boundary remain unchanged.
  The canary adds report fields additively; no stable 2.x audit-report or SARIF
  field or rule identifier is removed or renamed.

## Known issues

These predate 2.8.0 unless noted and are scheduled for 2.8.1 or 2.9.0.

- Running `mcp-audit scan` (also `pin`, `watch`, and the `serve` tools) inside a
  repository discovers that repository's `.mcp.json` and `.vscode/mcp.json` and
  connects to the servers they declare. In a checkout you do not trust, use
  `--skip-connect`. The GitHub Action already defaults to `skip-connect: true`.
- Server, tool, prompt, and resource names are printed to the terminal without
  stripping control sequences, and a name containing Rich markup such as
  `[/bold]` aborts the terminal report before `--json` output is written.
- Credential redaction (default and `--redact`) does not yet scrub secrets
  passed as a separate argument value (`--token VALUE`), bare token shapes, or
  URL query strings (`?access_token=VALUE`), and pin files store launch
  arguments verbatim.
  Review field reports by hand before sharing.
- Annotation-only changes (for example `readOnlyHint` flipping to `false`) are
  not detected by `--pin-check` or `--escalation-check`, because pins hash tool
  name, description, and input schema only. The runtime canary does compare
  annotations within a session.
- Remote (`url`) servers in Cursor, Windsurf, and Claude Desktop configs are
  reported as stdio servers with a missing command instead of being connected.
- A clean canary result does not list what it could not exclude (time,
  randomness, client identity, call count beyond the budget, later sessions),
  and the canary uses the SDK's default client identity. New in 2.8.0; the
  README describes these limits.
- `monitor` cannot proxy a real MCP stdio server (it uses `Content-Length`
  framing rather than newline-delimited JSON-RPC) and will be deprecated in
  2.9.0.

## Published-version boundary and rollback

The latest published package and Registry descriptor remain at 2.7.0 while
this candidate is reviewed. Retain `mcp-audits==2.7.0` as the rollback pin and
verify the installed command identity after any rollback.

## Required closure before publication

- Land the reviewed candidate on `main` with exact-head CI and CodeQL evidence.
- Build and verify wheel and sdist artifacts from the final clean revision.
- Promote release-state metadata from candidate to release in a separately
  reviewed publication change.
- Tag and publish only after the protected publication environment authorizes
  the exact release commit.
- Read back PyPI, GitHub Release, and MCP Registry identities independently.

## Claim ceiling

Repository consistency, local tests, and CI can establish candidate readiness
only. Tag, artifact publication, Registry uptake, installed runtime behavior,
live third-party interoperability, deployment, adoption, and human outcomes
remain unproved until their own exact readbacks exist. A clean canary describes
only its bounded in-session exercise, not the safety of a server in later
sessions.
