# Migrating from 2.x to 3.0

MCPAudit 3.0 removes surfaces that 2.11 and 2.12 deprecated with warnings. This
guide lists every break, what replaces it, and how to find it on 2.12 before you
upgrade. The decisions behind each break are recorded in the
[3.0 boundary proposal](3.0-BOUNDARY-PROPOSAL.md); the stable output rules are
in the [output contract](OUTPUT-CONTRACT.md).

Report formats do not change: the `AuditReport` JSON shape and
`schema_version`, the v2 pin format, signed pin manifests, policy and override
files, the `mcp-audits` package name, the `mcp-audit` and `mcp-audits` commands,
the `serve` tool names, and the `ScanOptions` library defaults all stay as they
were. Some reports gain additive warnings and SARIF results, described below.

## Before you upgrade

Do these on 2.12, which prints a warning for every surface 3.0 removes:

1. Read the stderr line that every `mcp-audit scan` run prints (in your CI logs
   or terminal). Replace each `scan` command with the `check` command from the
   [flag mapping](#scan-is-a-legacy-interceptor-over-check).
2. Refresh schema v1 pins: `mcp-audit pin --refresh SERVER`, review the diff,
   then rerun with `--apply`. 2.12 is the last line that can diff against a v1
   hash. See [v1 pins](#v1-pins-are-never-compared).
3. If you use labs, SafeForge or Proof Before Action, plan the new installs
   and import paths in [package split](#labs-and-proof-before-action-are-separate-distributions).
4. If an MCP client or agent calls the `serve` tool `scan_mcp_servers` and
   expects connections, pass `connect=true`.
5. Run your Python integration tests with `-W error::DeprecationWarning` to
   find calls to removed private entry points.

You do not need to change a pre-commit hook `rev` or an Action ref before
upgrading; see [CI integrations](#pre-commit-hook-and-github-action).

2.x keeps security-only fixes, with no features, on the `release/2.x` branch for
120 calendar days after 3.0.0; the package, the Action and the hook are
covered. See [continuous integration](guides/ci.md#command-grammar-and-release-tags).

## Breaking changes at a glance

| Break | Replacement | Detect on 2.12 |
| --- | --- | --- |

| Hidden lab, SafeForge and `skillscan` aliases removed | `mcp-audit lab TOPIC`, `mcp-audit safeforge preinstall` and `safeforge run`, `mcp-audit skills scan` | A stderr notice on each use; `mcp-audit --help-all` lists them |

| Action free-form `args` follow `check` grammar | Repeated `--client NAME`; `--output-json PATH` | 2.12 Actions already select `check` grammar and log the translation |

## `scan` is a legacy interceptor over `check`

`check` is the only review engine in 3.0. `scan` stays registered but hidden
from help. Every `scan` run classifies its parsed options before any discovery,
source read, connection or report write, and prints one notice on stderr.
Then one of two things happens:

- **Accepted (`preserved`, or `narrowed` by an explicit `--config-only`).** The
  notice prints the exact `check` command, and `scan` runs it through `check`'s
  parser. Output and exit codes are `check`'s.
- **Refused (`would-silently-shrink`), exit 2.** The notice starts with
  `scan: no exact check translation exists:` and gives the reasons. A second
  line prints a replacement command labelled **not exact; review before
  running**. Nothing is discovered, scanned, connected or written, and the
  replacement never runs automatically. An unsupported `--clients` spelling gets
  no replacement, because any runnable suggestion would widen the selection.

`scan` never connects in 3.0. Its 2.x default was to connect, so bare `scan`
and every form without `--skip-connect` are refused.

### Flag mapping

| 2.x `scan` form | 3.0 `check` replacement | 3.0 interceptor |
| --- | --- | --- |
| `scan` (discovers and connects to every workstation server) | `check --include-discovered --connect-all` | Exit 2, prints the replacement |
| `scan --skip-connect` | `check --include-discovered`, or `check --include-discovered --scan-compatible-sources` for scan's exact source selection | Runs `check --skip-connect --include-discovered --scan-compatible-sources` |
| `scan --skip-connect --inject-check` (the 2.11 pre-commit hook) | `check --include-discovered --inject-check` | Runs with `--scan-compatible-sources` |
| `scan --skip-connect --clients NAME` | `check --include-discovered --client NAME` | Runs with `--scan-compatible-sources` |
| `scan --clients a,b` | Repeated `--client a --client b` | Exit 2 (comma-separated selections are untranslatable) |
| `scan --json PATH` | `--output-json PATH` (`check --json` alone writes JSON to stdout) | Exit 2 |
| `scan --config FILE --config-only --skip-connect --override-config OVERRIDE` | `check --config FILE --override-config OVERRIDE` | Runs, narrowed to the named file |
| `scan --config FILE --config-only --skip-connect` (no `--override-config`) | `check --config FILE`, which loads no saved overrides; add `--override-config ~/.mcp-audit.yaml` to keep them | Exit 2 (config-only `scan` read default overrides) |
| `scan --config FILE --config-only` without `--skip-connect` | `check --config FILE --connect-all`, or `--connect --server ID` for one server | Exit 2 |
| `scan --config FILE --skip-connect` (no `--config-only`) | `check --config FILE --include-discovered` | Exit 2 (overlapping explicit and discovered sources can be lost) |
| `scan --connect-project-configs` | `check --include-discovered --connect-all --connect-project-configs` | Exit 2 |
| `scan --canary-check ...` | `check --config FILE --connect --server ID --canary-check` (or `--connect-all`), without discovery | Exit 2 |
| `scan` with any detector flag and no `--skip-connect`, for example `scan --pin-check` | `check --include-discovered --connect-all --pin-check` | Exit 2 |

Every other `scan` option has a `check` option of the same name. Options
outside the frozen translation table, and values that cannot be printed safely
on one line, are refused with exit 2.

Detectors that need served tool metadata (`--inject-check`, `--ssrf-check`,
`--egress-check`, `--pin-check`, `--trifecta-check`, `--shadow-check`,
`--escalation-check`) report `not_run` coverage in a static `check`, with a
reason that names why: usually `connections disabled`, and for `--pin-check` or
`--escalation-check` possibly `required per-server baseline unavailable` or
`check execution unavailable`. Add `--connect-all` or `--connect --server ID`
to keep the connected coverage that `scan` had. `--provenance-check`,
`--integrity-check` and `--verify-artifacts` compare configuration against the
pin baseline and run statically; `--verify-artifacts` still contacts the
package registries.

### The scan-compatible source selector (D22)

Plain `check --include-discovered` is the recommended static review. It limits
Claude Code project scopes to the selected project (cwd by default, or
`--project PATH`) and also reviews Cursor's project file.

`check --include-discovered --scan-compatible-sources` reproduces `scan`'s
server selection: every Claude Code `projects` scope, no Cursor project file,
cwd `.mcp.json` and `.vscode/mcp.json`, scan's whole-file loss when a sibling
Claude Code project entry is malformed, scan's server deduplication by name,
client, config and project, and an empty result (not a config-health
diagnostic) for a present file with no server map. Accepted static `scan` forms
translate to it.

The flag is hidden from help but supported for all of 3.x, because translation
notices print it. It requires `--include-discovered` and cannot be combined
with `--config`, `--project`, `--config-only`, `--connect` or `--connect-all`
(usage error, exit 2). Server identities under it omit the project path, so it
cannot select a connection. `--client` works with it. See
[migrating static scan commands](guides/scan-migration.md) for details.

D22 makes only the static discovering forms exact. It does not cover
`--json PATH`, comma-separated `--clients a,b`, `--config FILE` without
`--config-only`, config-only forms without `--override-config`, or any
connecting form. Rewrite those by hand from the table above.

### Detect before upgrading

2.12 prints the classification on every `scan` run without changing its
behavior. Read your existing logs:

- `scan: options map exactly to check ...: mcp-audit check ...` runs in 3.0.
- `scan: no exact check translation exists: ...` lists the reasons. On 2.12,
  discovering forms without `--clients`, or with `--clients claude_code` or
  `--clients cursor`, add one or both of two reasons that 3.0 resolves with
  `--scan-compatible-sources`: "Claude Code discovery can include other project
  scopes that check cannot select" and "check adds Cursor project discovery, so
  the selected server set can differ". If those are the only reasons, 3.0 runs
  the form. Any other reason means 3.0 exits 2.

`--scan-compatible-sources` does not exist in 2.12; on 2.12, use plain
`check --include-discovered`.

### Output differences for accepted `scan` forms

Accepted forms run `check`, so they look like `check`:

- Terminal output is `check`'s summary and requested details, not scan's
  report panel. `--verbose` and `--details` behave as in `check`.
- Each written artifact gets its own `Wrote PATH` line with the selected path,
  instead of scan's combined list of base names.
- `--card` writes `check`'s card and sticker output.
- Recheck suggestions name `check`, with explicit connection flags when a
  finding needs a connected review.
- Recovery errors use `check`'s format: what failed, where, recovery, whether
  scanning completed, the files already written, and the exit code.
- With no config sources at all (an empty home directory, as on most CI
  runners), the report carries the non-fatal `no_sources_reviewed` warning.
  The exit code is unchanged (see [zero sources](#zero-source-runs)).
- Run from the home directory, `scan` parsed `~/.vscode/mcp.json` twice and
  duplicated its diagnostics; `check` parses it once.
- A discovered source refused by `check`'s source limits is reported, not read.
  See [source limits](#source-limits-and-skipped-sources).

JSON, SARIF and HTML schemas are unchanged.

## Source limits and skipped sources

`check` refuses a discovered source that is a symlink (or has a symlinked
ancestor), is larger than 1,048,576 bytes, nests deeper than 64 levels, has
more than 20,000 containers, or has more than 1,000 servers (per source or
across accepted sources). `scan` read such sources. In 3.0, including
translated `scan` forms, a refused source produces:

- a `review_source_skipped` warning on stderr and in JSON;
- a HIGH `config_parse_failure` config-health finding and partial coverage;
- in the default `--sarif-profile compatibility`, one warning-level
  `MCP-CH-CONFIG-PARSE-FAILURE` result per skipped source, naming the reason and
  the remedy `--config FILE`, so SARIF dashboards such as GitHub code scanning
  show the reduced coverage. The `MCP-REVIEW-SOURCE-SKIPPED` invocation
  notification and `executionSuccessful: true` stay. The `extended` profile
  keeps its existing error-level config-health result and adds no duplicate.

A symlinked or oversized `~/.claude.json` is a common case. Because the skip is
a config-health finding, a `fail_on.config_health` policy exits 2 where `scan`
exited 0. To review such a source, select it explicitly with `--config FILE`;
explicit files may resolve a symlink but keep the size, nesting and server
limits.

## Zero-source runs

A `check` run that accepts no config source adds the `no_sources_reviewed`
warning (`check: config_health`) and exits as before; it does not fail. CI
runners usually have no MCP configs, so the hook and the Action often produce
this warning. Select the intended sources with `--config FILE` or
`--project PATH` if an empty review should not pass silently in your pipeline.

## Pre-commit hook and GitHub Action

Your hook `rev` and Action ref decide what runs, not your local install:

- **Unaffected until you bump.** A hook pinned to a 2.x `rev` installs that 2.x
  package and keeps its own entry; a 2.11 `rev` keeps running
  `scan --skip-connect --inject-check` on 2.11. An Action ref pinned to 2.x
  installs the version in that ref's `pyproject.toml`, unless you set the
  `version` input. Do not rewrite a 2.11 hook to another command; bump `rev`
  when you are ready. A 2.10 or 2.11 Action ref still assembles `scan`
  grammar, so pairing it with a 3.x `version` fails on the `json`, `config` or
  comma-separated `clients` inputs; bump the ref together with the version.
- **After the bump, the hook runs** `mcp-audit check --include-discovered
  --inject-check` (since 2.12). The Action runs `mcp-audit check
  --include-discovered` with its inputs (and `--skip-connect` by default). Both
  review the selected project (the repository root, or the Action's
  `working-directory`), not scan's set of every Claude Code project scope, and
  they also review Cursor's project file. They do not pass
  `--scan-compatible-sources`.
- **The Action installs only `mcp-audits`.** Labs are not installed, and
  `args` is appended to `mcp-audit check`, so `lab` commands through Action
  `args` are not supported. Run labs in a separate step after
  `uv tool install 'mcp-audits[labs]'`.
- **Action `args` follow `check` grammar** whenever the installed package has
  the expanded `check` options (2.12 and newer, including a 2.12 Action ref with
  a 3.x `version` input). Legacy `--json PATH` and a single `--clients NAME` are
  translated with a logged notice; `--clients a,b` exits 2. With the default
  `skip-connect: "true"`, connection flags in `args` fail. See
  [continuous integration](guides/ci.md#command-grammar-and-release-tags).
- A requested pin-dependent check with a withheld baseline makes the Action
  exit 2 after its reports are written and SARIF is uploaded; see
  [v1 pins](#v1-pins-are-never-compared).

## v1 pins are never compared

A genuine schema v1 pin entry is withheld from every pin-dependent check
(`--pin-check`, `--canary-check`, `--escalation-check`, `--provenance-check`,
`--integrity-check`, `--verify-artifacts` and `--download-artifacts`), whether or
not trusted pin keys exist. 2.x still compared v1 entries when no trusted key
was configured; that comparison stops. A withheld entry gets a
`pin_baseline_withheld` warning naming the server and the refresh command, and
partial coverage, never a pass. It does not satisfy `require.pins`. In a mixed
entry, v2 rows still compare and v1 rows are excluded from drift and named by
`pin_schema_outdated`. The pin file is never rewritten on read.

**Withheld baselines fail the run.** In `check` (including accepted `scan`
forms) and `shadow`, a requested pin-dependent check whose baseline is withheld
exits 2 after reports are written, even without `--policy`. `policy_result`
records the violation (`fail_on.pin_baseline_withheld`, HIGH, rule `MCP010` in
SARIF), so JSON is never `null` alongside that exit. An explicit
`fail_on.pin_baseline_withheld: false` is accepted but ignored, with a loader
warning; it is not a schema error. A check that you did not request never fails
the run.

`watch` never exits for this: its implicit pin check renders the warning and
writes reports with partial coverage on every loop. Library callers of
`run_scan`, library policy evaluation and `serve` do not get this gate.

**Migrate:**

1. On 2.12, run `mcp-audit pin --refresh SERVER`, review the diff against the
   v1 baseline, then `mcp-audit pin --refresh SERVER --apply`.
2. On 3.0, a remaining v1 entry has no comparable baseline. `pin --refresh
   SERVER` shows the full current surface as a new pin; `--apply` writes a v2
   entry, signed when a trusted key is configured.

**Detect on 2.12:** `pin_schema_outdated` and `pin_baseline_withheld` warnings
in the terminal and the JSON `warnings` array name affected servers. Setting
`fail_on.pin_baseline_withheld: true` previews the failure for `--pin-check`;
3.0 applies it to all seven checks.

## Labs and Proof Before Action are separate distributions

| Distribution | Import package | Command |
| --- | --- | --- |
| `mcp-audits` | `mcp_audit` | `mcp-audit`, `mcp-audits` (review, `serve`, `watch`, pins, policy, `skills scan`) |
| `mcp-audits-labs` | `mcp_audit_labs` | none; `mcp-audit lab ...` and `mcp-audit safeforge ...` load it |
| `mcp-audits-proof` | `proof_before_action` | `proof-before-action` |

`uv tool install mcp-audits` installs core only. Install the others like this:

```sh
uv tool install 'mcp-audits[labs]'   # core plus labs and SafeForge
uv tool install mcp-audits-proof     # puts proof-before-action on PATH
```

A `uv tool` extra does not expose another distribution's scripts, so
`mcp-audits[proof]` alone does not put `proof-before-action` on `PATH`; install
`mcp-audits-proof` as its own tool. In a virtual environment,
`pip install 'mcp-audits[labs,proof]'` or `mcp-audits[all]` (which also adds the
`watch`, `llm` and `otel` extras) installs everything. Labs pin core to the same
version.

Without labs, `mcp-audit lab ...`, `mcp-audit safeforge ...` and the conformance
probe exit 2 with the install command. `watch` without its optional
`watchfiles` dependency still exits 1 with the `mcp-audits[watch]` hint, a
known inconsistency kept for compatibility.

## `serve` tool reach

`scan_mcp_servers` defaults to a static audit: its `connect` argument defaults
to `false`. Pass `connect=true` to connect to workstation-scope servers;
`skip_connect=true` always disables connections. The report shape is
unchanged. Every other tool keeps its 2.x reach, and its description states it:

| Reach | Tools |
| --- | --- |
| Connects to workstation-scope servers | `get_high_risk_servers`, `check_server` (the named server only), `get_injection_findings`, `get_ssrf_findings`, `get_trifecta_findings`, `get_shadowing_findings`, `get_escalation_findings`, `get_provenance_findings` |
| Static, no network | `list_discovered_servers`, `get_integrity_findings` |
| Static toward MCP servers; contacts npm and PyPI registries only | `get_package_verify_findings`, `get_artifact_verify_findings` |

`serve` loads no policy and sets no exit code. A withheld pin baseline is a
`pin_baseline_withheld` warning (partial coverage), never a tool error.

## Exit codes

| Code | Meaning | Reports written? |
| --- | --- | --- |
| `0` | The review completed and no applicable policy gate failed. Exit 0 does not certify security. | Yes |
| `1` | Setup or input/output failure, such as an invalid client, policy or override file, or a failed artifact write. The error names the failed stage, recovery, scanned state and written paths. | Only those listed as written |
| `2`, before anything runs | Usage or artifact-path validation failed, or the `scan` interceptor refused a form. | No |
| `2`, after reports | A policy gate failed, including the withheld-pin gate for a requested pin-dependent check (with or without `--policy`) in `check`, accepted `scan` forms and `shadow`. | Yes |

Tell the two exit-2 cases apart in CI by stderr and artifacts: an interceptor
refusal prints `scan: no exact check translation exists:` and a
`scan: replacement command` line and writes nothing, while a policy failure
writes the requested JSON, SARIF, HTML and card outputs first and records the
violations in `policy_result`. A missing labs distribution also exits 2 with
the install command. `watch` does not exit for withheld pins, and `serve`
tools never set an exit code. Experimental lab commands document their own
exit codes in the [output contract](OUTPUT-CONTRACT.md#exit-codes).
